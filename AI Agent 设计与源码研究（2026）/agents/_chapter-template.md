# Agent 源码教学章节模板

> 本文件用于扩展和重写课程，不属于学习主线。模板约束教学闭环，不要求所有项目拥有完全相同的章节结构。

## 使用原则

1. 一个项目只承担 1–3 个最有迁移价值的设计问题；不要复述完整 README。
2. 章节顺序由知识依赖决定，项目热度、评分和收录过程留在研究附录。
3. 先写正常路径，再写失败或恢复路径；只有静态架构图不足以教会运行时语义。
4. 源码证据固定到 commit，并优先链接真正拥有控制流、状态或权限的实现。
5. 补充内容以减少理解成本为目标：优先增加 trace、不变量、反例和验收，不机械增加篇幅。
6. 如果项目有独特机制，可以增加专属章节；如果某个模板段落没有教学价值，可以省略。

---

**章节标题：第 N 章 项目名——本章负责讲清的机制**

> 参考实现、冻结提交、许可证与必要的版本状态。

## 本章要解决的问题

用两段以内说明：前章留下了什么问题，本章为什么需要引入新的状态、接口或运行时边界。

## 本章目标

| 问题 | 建议 |
|---|---|
| 本章重点 | 1–3 个核心机制 |
| 前置知识 | 优先引用前面章节；外部概念按需引入 |
| 第一遍重点 | 3–5 个源码入口或关键对象 |
| 可以后看 | provider、UI、部署或不影响主线的扩展 |
| 完成后应能回答 | 3 个可以脱离框架 API 回答的问题 |

## 核心设计

放一张最小架构图。图中必须能看出：决策者、状态 owner、动作执行者、持久化边界和外部世界。

## 两条源码调用链

1. **正常路径**：从入口到终止结果；
2. **失败/恢复路径**：从错误、暂停或崩溃点到重新进入循环。

## 建议源码阅读顺序

给出 3–7 个固定提交入口。每一步都说明要验证的问题，不写成目录清单。

## 机制解剖

按项目特性组织，可使用状态表、时序图、对象关系、crash-window matrix 或等价伪代码。至少回答：

- 谁决定下一步？
- canonical state 在哪里？
- 失败后哪些代码或副作用会重跑？
- 权限在哪里收紧？
- 什么条件才算真正完成？

## 关键不变量与失败路径

只保留能指导实现或测试的不变量。每条最好可以转成断言、故障注入或回归测试。

## 设计收益

说明这些机制解决了什么结构性问题，以及为什么比更简单的实现多出这一层复杂度。

## 适用边界与常见误区

区分框架状态与外部世界状态、审批与隔离、功能存在与可靠性已验证。项目成熟度和社区数据仅在会改变采用风险时简短说明。

## 本章练习

练习应复刻核心机制，不复刻整个框架，并遵循[课程实验协议](../exercises/README.md)。至少包含一个本地确定性 fixture、一条正常 trace 和一个真实故障注入。

### 练习验收

- 明确产物：代码、trace、状态图或测试；
- 明确可观察结果：什么行为说明实现正确；
- 明确失败条件：怎样证明恢复、安全或终止边界没有被误解。

## 检查理解

写 3–5 个检索问题。问题应要求学习者从记忆解释所有权、恢复和边界，不能只复述类型名。

## 本章小结

用一段话压缩本章唯一需要长期保留的心智模型，并连接下一章为什么出现。
